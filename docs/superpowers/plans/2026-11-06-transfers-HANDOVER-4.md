## What each task built

**T15** (server, Opus implementer + dedicated Opus reviewer) — a new, independent settings gate, `show_tours: boolean` (default `false`), alongside `content_unverified`. Added to `SETTING_SCHEMAS`/`SETTING_KEYS`/`SEED_SETTINGS`/`SettingsPayload`. Gates five public consultation points — `tours.list` (returns `[]`), `tours.bySlug` (refuses `NOT_FOUND`, byte-identical to the unknown-slug message), `checkout.quote`'s tour path and `checkout.createHold`'s tour path (both reuse 100% existing error vocabulary — zero new error classes, zero new guest-facing strings), the SEO resolver (`/tours`, `/tours/:slug` → 404/noindex), and the sitemap (omits both). Two load-bearing design rulings, both implemented and independently mutation-proved by the controller/reviewer: (1) `readSettings()` — and therefore the public `settings.get` every page calls — never throws on a missing `show_tours` row, which would otherwise be a site-wide outage on the first deploy before `db:seed` re-runs; (2) the test harness gets its own baseline (`true`, via a new `seedTestBaseline()` helper used by both `global-setup.ts` and `resetTestDb()`), kept deliberately separate from the real product seed (`false`) — mirroring the existing `ALLOW_DEMO_SEED` precedent, needed because `SEED_SETTINGS` is shared verbatim between the app and test databases and ~a dozen pre-existing tours/checkout/SEO/sitemap test files assume a visible catalog.

T15 reported **NEEDS_CONTEXT**, not DONE, correctly: one pre-existing client guard test (`admin-settings-page.test.tsx`, "every shared settings key has exactly one group and one block") stayed red until T16 added the UI block — there was provably no way to make T15 alone green without either a misleading shim or a silently-broken Save, both explicitly rejected and explained in the implementer's own report. The dedicated Opus reviewer confirmed this reasoning was sound and approved T15 on that basis.

**T16** (client, Sonnet implementer + combined Sonnet review) — closed T15's gap and built the rest. ## Rulings made this batch (controller decisions on your behalf — read these)

1. **`show_tours` seeds `false` in the real database; the test harness alone gets `true`.** Confirmed by direct measurement (not guessed) that seeding `false` for real would break roughly a dozen pre-existing test files that assume a visible tour catalog, since `SEED_SETTINGS` is shared verbatim between app and test databases. Fixed at the one choke point that actually matters — `resetTestDb()` wipes and re-seeds the whole `settings` table, so the test-baseline flip had to live inside the function that does that, not as a one-time `global-setup.ts` patch (which 4 of the ~12 affected files would have silently undone mid-run). Cost if wrong: none for production (the seeded default is exactly what the plan asked for); a change to this split would need re-auditing the same ~dozen test files.
2. **`readSettings()` gets a second narrow fail-safe carve-out, alongside the existing `transfer_operations` one.** Without it, `show_tours` joining `SETTING_SCHEMAS` would make `getSettingsPayload()` — i.e. every page's `settings.get` — throw on any database that hasn't re-run `db:seed` yet, a site-wide outage rather than a tours-only one. Cost if wrong: reverting this one `continue` branch re-exposes that outage window; the carve-out is narrow and already pinned by its own test (`settings.test.ts`'s "missing row does NOT take settings.get down" test, independently reproduced by the T15 reviewer by reverting the carve-out live and watching that one test — and only that one — go red).
3. **`show_tours` lives in the `business` settings group, beside `transfer_operations`, not in `site-seo` beside `content_unverified`.** Both placements were defensible (the brief offered either); `business` was chosen because `show_tours` and `transfer_operations` are the same feature launch and an owner managing it will look for both together. Cost if wrong: moving one entry between two existing groups, no schema/data impact.
4. **`MostVisited` is hidden entirely when tours are off, not repointed to transfers.** Its only links go to `/tours?destination=...`; repointing six destination tiles into `/transfer` would need either a transfer-route-to-destination mapping that doesn't exist yet for most destinations, or a generic link that contradicts the section's own promise ("the destinations our vans run to most"). Hiding was the simpler, honest choice — not the only one. Cost if wrong: a design decision about what (if anything) replaces this section while tours are off, isolated to `HomePage.tsx`/`MostVisited.tsx`.
5. **The Hero's tour-search form is gated on `showTours !== false`, not `?? false` like every other gate in this task.** `HeroSection.tsx` carries a pre-existing, test-pinned contract ("renders unconditionally, with no dependency on settingsQuery having resolved") specifically because it's above the fold on a slow mobile connection — `?? false` would silently break that contract during ordinary loading, which the brief never asked for and which three existing tests would have caught as a regression. This was the implementer's own call, made because the component's own comment resolves it rather than because it was genuinely ambiguous; documented in the code at both ends (`HeroSection.tsx` and `SiteHeader.tsx`'s comments cross-reference each other). Cost if wrong: one conditional's comparison operator, isolated to one component.
6. **Two Important review findings on T16 were parked as documentation fixes, not sent through a fix round.** Both the "layout shift when tours are flipped back ON" finding and the "`performance-markup.test.tsx` has a second undisclosed coupling" finding ask for better notes on a deliberate, correctly-reasoned trade-off — not a code change — and the reviewer's own verdict was "recommend: approve." Writing them into this handover and the ledger is the controller's own bookkeeping, not a bypassed code review. Cost if wrong: these resurface as real findings the next time someone touches this area, costing a re-discovery, not a regression.

## Open owner questions

1. **(New, the most important one) Two public procedures leak whether a specific tour exists while `show_tours` is off, and need one ruling, not two.** `checkout.availability` (flagged by T15's own implementer, out of scope by design) and `reviews.forTour` (found independently by T15's dedicated reviewer, worse — it returns a tour's full review payload: bodies, guest names, star breakdown) both resolve a tour slug on their own, bypassing the `show_tours` gate. Neither moves money or exposes anything beyond what a VISIBLE tour already shows; both are capacity/content disclosure only. The reviewer's recommended shape is a single owner-ruled follow-up task: enumerate every public procedure that resolves a tour slug independently (today: these two), and fix the SET of them in one pass — e.g. one shared `resolvePublicTourBySlug()` helper so a future seventh such procedure can't miss the gate, rather than a sixth independent `readShowTours()` call bolted on ad hoc. **Pair this with question 2 below when asking the owner** — both are "what should actually be true while `show_tours` is off" questions, and answering them together avoids two separate follow-up tasks for the same underlying switch.
2. **(New) Is `show_tours` defaulting OFF, with the owner flipping it on later via the admin screen, actually how the owner wants to launch — or is there a different rollout sequencing in mind?** This batch built exactly what the plan specified (OFF by default, admin-toggleable), but confirm this still matches the owner's current launch plan before relying on it, especially alongside question 1 above (an owner who wants tours genuinely invisible everywhere, not just mostly, needs question 1 resolved first).
3. **(New, a precondition on a FUTURE task, not a question needing an answer now)** Before anyone runs the task that flips `show_tours` ON for real (whenever that is), they should know: every `show_tours` gate in T16 except the hero form defaults to HIDDEN while `settings.get` is still loading (`?? false`). This is invisible today (nothing to pop in while the product ships OFF) but means the first real "tours ON" deploy will show a brief layout shift on every page load — the "Tours" nav link and the home page's `CatalogPreview`/`MostVisited` sections popping in after the settings query resolves, in a codebase that otherwise guards carefully against exactly this (see `performance-markup.test.tsx`, and `HeroSection.tsx`'s own refusal to do this for above-the-fold content). Not a defect to fix now; a known cost of turning the switch on, to be weighed then — likely a non-issue if the switch is flipped rarely and off-peak, worth a second look if it's expected to be flipped casually.
4. **(Carried, unanswered since Handover 3)** Day-use overrun legal/content gap (plan's Legal & content to-dos #4).
5. **(Carried, unanswered since Handover 3)** "Operated by R&G Travel & Tours" regulatory language for transfers (plan's Legal & content to-dos #6).
