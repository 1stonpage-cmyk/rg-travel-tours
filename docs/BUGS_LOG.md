# Bugs Log — TravelSugbo / R&G Travel & Tours

Every defect found on this project, including ones caught in planning or review
**before they shipped**. A bug that was caught by a review still belongs here — the
point of the log is to show where defects come from, not only which ones escaped.

**Keep this updated.** Append a row when a bug is found; update its status when it is
fixed. One row per bug.

**Severity:** `critical` = data loss, a security control that does not work, or a
production outage. `important` = wrong behaviour, a missed requirement, or a test that
cannot fail. `minor` = polish, coverage gaps, and cosmetics.

**How found** is the most useful column over time. So far: `review` dominates, which is
the process working; `controller` entries are ones caught by verifying claims against
live data rather than reading a report; `plan` entries are defects in the implementation
plan itself, several of which would have shipped as "passing" code.

| BUG-119 | 2026-10-30 | Pre-launch / B5 | **All three app surfaces shared ONE session cookie, so signing into one evicted the others.** `server/src/middleware/session-cookie.ts` issued `rg_session` with one name and one path for all three subject types, and `sessions.subject_id` is polymorphic — so a guest signing into "My Booking" (`portal.login`) in the same browser **overwrote a live staff session**, a driver sign-in overwrote both, and so on. ## Standing design decisions — deliberately not enforced in the database

Not bugs, and not deferrals either: these are places where the owner chose code-level enforcement
over a database constraint, on purpose. Recorded so a later reader does not "fix" them.

| Decision                                        | Date       | What is NOT in the database                                                                                                                                                                                                                        | Where it IS enforced, and why there                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Cross-column money invariants on `bookings`** | 2026-10-12 | No `CHECK` relating one money column to another — nothing stops `total > subtotal`, or `amount_paid > total`, at the DB level. The **sign** is constrained (`bookings_*_non_negative`, `payments_amount_positive`); the **relationships** are not. | `recordPayment()` already refuses an overpayment inside the booking row lock, and the future booking service owns the subtotal/discount/total arithmetic. The owner's call (2026-10-12): keep it in code. A cross-column CHECK would have to be re-stated for every path that writes money and would fight the price-snapshot design, where the authoritative figures are frozen in JSON rather than recomputed. The trade-off accepted knowingly: a direct `UPDATE` run by hand in a SQL client can still produce an inconsistent row, and only the service layer stops it. |
